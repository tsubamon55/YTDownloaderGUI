# YouTube ライブ配信の録画 設計

## 目的

配信中の YouTube ライブを、配信が終わるまで(またはユーザーが止めるまで)リアルタイムに保存できるようにする。配信の開始時点からさかのぼって取得できる配信では、それを既定にしつつ「今から」も選べるようにする。録画中のタスクはダウンロード一覧の上部に固定し、件数が増えても見失わないようにする。

## 成功条件

- 配信中のライブの URL を入力すると、ライブであることと配信開始からの経過時間が表示され、「録画開始」で録画が始まる。
- さかのぼれる配信では「録画開始位置」に「配信の最初から」(既定)と「今から」が出る。さかのぼれない配信ではその旨だけが表示され、今から録画する。
- 録画中は一覧の上部の固定領域に表示され、さかのぼり取得中は割合、追いついた後・今からの録画では録画時間とサイズが出る。
- 「停止」(確認あり)で録画を止めると、それまでの分が再生できるファイルとして保存される。配信が終わった場合も同様に保存される。
- 録画中にアプリを閉じると、確認の上で停止・保存を終えてから終了する。
- 通常の動画のダウンロードの動作・表示は変わらない。既存テストが通り、`ruff` と `mypy` が通る。

## 前提として確認した yt-dlp の挙動(2026.08.19、配信中の `rEXvVAjUYaE` で検証)

- `extract_info(download=False)` で `live_status == "is_live"`、`is_live == True`、`release_timestamp`(配信開始時刻)が得られる。`duration` は `None`。
- 通常の抽出では、フォーマットは `m3u8_native` の HLS で、**映像のみ(例: 311 = 720p、312 = 1080p)と音声のみ(233 / 234)が別々**になっている。`bv*+ba/b` は `311+234` のような組み合わせを選ぶ。タイトルの末尾には yt-dlp が現在日時(`2026-10-02 19:06`)を付ける。
- `live_from_start=True` で抽出すると、さかのぼれる配信では `http_dash_segments_generator` の DASH フォーマット(`is_from_start`、区切り2秒)だけが残る。さかのぼれない配信では `--live-from-start is passed, but there are no formats that can be downloaded from the start` の `ExtractorError` になる。タイトルに日時は付かない。抽出はどちらも1秒台。
- **配信の最初から(DASH)**
  - 進捗フックに `fragment_index` と `fragment_count`(配信開始からの区切りの総数。配信が進むと増える)が渡る。
  - 進捗フックから `KeyboardInterrupt` を送出すると、映像・音声の両スレッドが止まり、`download()` は 0 を返し、結合(Merger)まで行われて再生可能な mp4 になる。作業フォルダには `.part-Frag*.part` が残る。
  - `concurrent_fragment_downloads` を 4 や 8 にすると、`KeyboardInterrupt` を送出しても止まらずに固まり、取得も速くならなかった。**既定の 1 のまま使う。**
  - 取得速度は 720p で実時間の約6〜7倍(2時間分で20分前後)。
- **今から(HLS)**
  - yt-dlp はライブの HLS を `FFmpegFD` に渡し、`proc.wait()` で待つだけのため、進捗フックが呼ばれず、フックからは止められない。
  - 選ばれた各フォーマットの `url` と `http_headers` を ffmpeg に `-headers … -i URL` で入力し、`-map 0 -map 1 -c copy -f mpegts` で録画できた。`-progress pipe:1` で `total_size` / `out_time` が得られ、標準入力に `q` を書くと約2秒で終了コード 0 で止まり、`.ts` から mp4 への `-c copy` の再格納も成功した。
- `quiet: True` だけではライブの進捗表示が標準出力に出続けるため、`noprogress: True` も要る。

## 採用しなかった案

- **今からの録画も yt-dlp に任せる**: 進捗が出ず、フックから止められない。止めるにはスレッドへ非同期例外を送る等が必要だが、`proc.wait()` の待機中は届かない。
- **yt-dlp を別プロセスで動かしてシグナルで止める**: 今の `DownloadWorker`(作業フォルダ・進捗・キャンセル)の作りを全面的に変えることになり、変更が大きすぎる。
- **区切りの並列取得でさかのぼりを速くする**: 上記のとおり停止できなくなる。

## 設計

### 情報取得 `FormatListWorker`(`src/workers.py`)

- 通常どおり抽出した結果が `live_status == "is_live"` の場合だけ、`live_from_start=True` でもう一度抽出する。成功すればさかのぼり可能、`ExtractorError` なら不可とする。
- `finished_ok` に5番目の値として `LiveInfo | None` を追加する。`LiveInfo` は、Qt・yt-dlp に依存しないライブ関連の計算(タイトルの日時の除去・さかのぼりの進み具合・進捗の文言)とともに新規の `src/live.py` に置く。
  ```python
  @dataclass(frozen=True)
  class LiveInfo:
      started_at: float | None        # 配信開始時刻(UNIX時刻、release_timestamp)
      can_record_from_start: bool
  ```
- タイトルは日時の付かない方(さかのぼり用の抽出結果、不可なら通常の抽出結果から末尾の日時を除いたもの)を返す。
- `live_status == "is_upcoming"` は `finished_error` で「配信開始前です。配信が始まってから再度お試しください」を返す。yt-dlp は配信開始前のライブに対して info を返さず `This live event will begin in …` のエラーを送出することが多いため、この文言を含むエラーも同じ案内に置き換える。
- `post_live`(配信終了直後でアーカイブ処理中)・`was_live` は通常の動画として扱う(yt-dlp が自動で DASH を処理する)。

### ダウンロード要求 `DownloadRequest`

- `live_mode: Literal["from_start", "from_now"] | None = None` を追加する。`None` は通常の動画。

### 録画の共通の振る舞い `DownloadWorker`

- 外向きのシグナル(`progress` / `log` / `finished_ok` / `finished_error` / `cancelled`)は変えない。追加するのは次の1つ。
  - `live_state_changed = pyqtSignal(bool)`: 録画中なら True。停止を受け付けた時・配信が終わった時に False を送る(一覧の固定を外すため)。
- `cancel()` はライブでは「停止して保存」の意味になる。止めた後は成功時と同じ経路(作業フォルダから保存先へ移す → `finished_ok`)で終わる。録画が1秒も取れていない場合は `finished_error`(「録画できたデータがありません」)。
- ライブでは `noprogress: True` を付ける(通常の動画でも害はないため `_base_ydl_opts` に入れる)。
- 進捗の文字列は、狭い一覧に収まるよう次の形にする。
  - さかのぼり取得中: `さかのぼり取得中 37%`(割合は進捗バーにも出す)
  - 録画中: `録画中 12:34 · 345MiB`(進捗バーは割合なし)
  - 停止後: `保存しています...` / 配信終了時: `配信終了・保存しています...`
- 割合と録画中の区別は `progress` シグナルの `percent` で伝える。`percent < 0` を「割合なし(録画中)」とし、`DownloadTaskWidget` はバーを不定(アニメーション)にする。

### 配信の最初から(`live_mode="from_start"`)

- 既存の yt-dlp の経路に `live_from_start=True` を加えるだけで、作業フォルダ・ファイル名・結合・保存先への移動はそのまま使う。`concurrent_fragment_downloads` は指定しない(既定の 1)。
- 停止: 停止が要求されたら、以降の進捗フックの呼び出しでは毎回 `KeyboardInterrupt` を送出する(映像・音声の両スレッドをそれぞれ止めるため)。通常の動画のキャンセルは今までどおり `DownloadError`。
- 進捗: 映像と音声のうち遅い方の `fragment_index / fragment_count` をさかのぼりの割合とする。両方が `fragment_count - 3`(約6秒分)以上に達したら追いついたとみなし、以降は「録画中」表示にする。録画時間は `fragment_index × 2秒` ではなく、録画開始からの経過時間+さかのぼった時間(配信開始時刻からの経過)で表す。
- ファイル名: タイトル(日時なし)のまま。同名があれば今までどおり ` (1)` を付ける。

### 今から(`live_mode="from_now"`、新規 `src/live_recorder.py`)

- `DownloadWorker` が `_probe` で選ばれたフォーマット(`requested_formats` があればその各要素、なければ info 自体)を `LiveRecorder` に渡し、作業フォルダ内で録画させる。
- `LiveRecorder`
  - ffmpeg を `Popen(stdin=PIPE, stdout=PIPE)` で起動する(Windows でコンソール窓を出さないよう `yt_dlp.utils.Popen` を使う。`clip_trimmer.FFmpegRunner` と同じ)。
    `ffmpeg -hide_banner -loglevel error -nostats -progress pipe:1 [-headers H -i URL]... -map 0 [-map 1] -c copy -f mpegts rec.ts`
  - `-progress` の出力から `total_size` と `out_time` を読み、コールバックで `DownloadWorker` に渡す。
  - 停止: 標準入力に `q` を書いて終了を待つ。30秒で終わらなければ強制終了する(`.ts` はそれまでの分が再生できる)。
  - 配信が終わると ffmpeg は自分で終了する。終了コードが 0 以外でも、`.ts` に中身があれば保存を続け、ログに警告を残す。
  - 録画後、`.ts` を `-c copy -map 0` で `<タイトル>.mp4`(音声のみの形式では `.m4a`)に再格納し、`.ts` は作業フォルダごと消える。mp3 の形式では、その後に既存の mp3 変換(FFmpegExtractAudio と同じ設定)を ffmpeg で行う。
- ファイル名: yt-dlp が付けた日時入りのタイトルを使う(同じ配信を何度か録画しても区別できる)。
  配信の最初から最後までを録画できなかった場合は、切り抜きと同じ表記で録画した範囲(配信開始からの時刻)を付ける(例: `[0_59-1_13]`。最初から録画した場合は `[-1_13]`、最後まで録画した場合は `[0_59-]`)。
- 入れ替えた後、通常のダウンロードと同じくサムネイルを埋め込む(yt-dlpの `EmbedThumbnail` を直接使う)。取得・埋め込みに失敗しても録画は保存し、ログに残す。`.ts` のまま保存する場合は埋め込まない。

### メイン画面(`src/main_window.py`、`src/main_window_ui.py`)

```
URL: [https://www.youtube.com/live/rEXvVAjUYaE        ] [貼り付け]
┌────────┐ ● LIVE  配信開始から 1:59:30
│サムネ  │ 【逆凸】加入2日目！事務所メンバー全員に…
└────────┘
形式: [動画 (最高画質 mp4)        ▾]
録画開始位置: (●) 配信の最初から（1:59:30 さかのぼる）  ( ) 今から
保存先: [C:\Users\...\Downloads              ] [参照...]
[                 録画開始                 ]
⟳ 配信中のライブを検出しました                       ログ ▾
```

- タイトルの上に、赤い「● LIVE」と、控えめな文字色の「配信開始から 1:59:30」を出す。経過時間(`clip_range.format_clip_time` の `H:MM:SS` 形式)は1秒ごとの `QTimer` で更新し、ライブの情報を表示している間だけ動かす。開始時刻が分からない場合は「● LIVE」だけを出す。
- ライブでは「手動設定」と「詳細設定」(切り抜き範囲)のトグルを**非表示**にする(開いていれば閉じる)。手動設定のフォーマット ID はさかのぼり用(DASH)と今から用(HLS)で異なり、切り抜きは長さが決まらないため使えない。URL がライブ以外に変わると元に戻す。
- 「形式」の直下に「録画開始位置」の行をライブのときだけ出す。
  - さかのぼれる場合: ラジオボタン「配信の最初から（H:MM:SS さかのぼる）」(既定)と「今から」。
  - さかのぼれない場合: ラジオボタンの代わりに、控えめな文字色で「今から録画します（この配信はさかのぼって保存できません）」。
- ダウンロードボタンの文字を「録画開始」にする。状態表示は「配信中のライブを検出しました」。
- ライブの形式のプリセットはそのまま使う(`bv*+ba/b` 等は DASH・HLS どちらでも選択できる)。1080p 超の確認ダイアログも今までどおり。
- 録画開始後は、通常のダウンロードと同じく URL 欄を空にする。

### ダウンロード一覧(`src/widgets.py`、`src/main_window_ui.py`)

```
ダウンロード
┌ 固定領域(スクロールしない)────────┐
│[サムネ] 【逆凸】加入2日目！…        │
│▓▓▓▓▓▓░░░░░░░░ (赤)                 │
│● LIVE さかのぼり取得中 37%    停止 │
└────────────────────────────────────┘
┌ スクロール領域 ────────────────────┐
│ 通常のダウンロード(新しい順)       │
```

- 一覧の見出しとスクロール領域の間に、録画中のタスクを入れる固定領域(`pinned_list_layout`)を置く。中身がない間は隠す。スクロール領域の外なので、通常のダウンロードが何件あっても常に見える。
- `DownloadTaskWidget` にライブ表示を追加する(`set_live(True)`)。
  - 状態の行の先頭に赤い「● LIVE」。進捗バーを赤にする。
  - `set_progress` で `percent < 0` のときはバーを不定(`setRange(0, 0)`)にする。
  - ボタンの文字は「停止」。押すと `stop_requested` を送り、`MainWindow` が「録画を停止して保存しますか?」(はい/いいえ、既定はいいえ)を確認してから止める。
- `live_state_changed(False)` を受けたら、ライブの表示(バッジ・赤)は保ったまま、タスクを固定領域からスクロール領域の先頭へ移す。完了後は通常と同じ「完了 / フォルダを開く / 閉じる」。

### アプリの終了(`MainWindow.closeEvent`)

- 録画中のタスクがある場合の確認文: 「録画中のN件を停止・保存し、ダウンロード中のM件を中止して終了しますか?」(該当する方だけ書く)。
- 「はい」なら、録画は停止(保存)、通常のダウンロードは今までどおりキャンセルする。録画の保存(結合・再格納)が終わるまで、モーダルの「保存しています...」を出し、**時間の上限なし**で待つ。通常のワーカーの待ち時間の上限(10秒)は今までどおり。
- 待っている間もイベントループを回すため、`QThread.wait()` で止めるのではなく、録画ワーカーが全部終わったら改めて `close()` を呼ぶ形にする(1回目の `closeEvent` は `ignore` する)。

## エラー処理

- 今からの録画で、通信断・URL の期限切れなどで ffmpeg が止まった場合、それまでに取れた分(`.ts`)があれば保存して完了とし、ログに理由を残す(録画は途中で途切れても、取れた分に価値があるため)。何も取れていなければ失敗として扱う。
- 配信の最初からの録画では、区切り単位の取得失敗は yt-dlp が読み飛ばして続ける(`skip_unavailable_fragments` の既定)。それでも yt-dlp が例外で止まった場合は、結合前の断片しか残らないため、通常のダウンロードと同じ失敗の経路で扱う。
- さかのぼり可否の確認(2回目の抽出)が通信エラーで失敗した場合は、さかのぼれないものとして扱い、ログに残す。

既存の `tests/` の方針(yt-dlp・Popen・QThread はモックし、ネットワークに出ない)に合わせる。

  - 最初からの録画: 停止後のフックが毎回 `KeyboardInterrupt` を送出する、通常の動画のキャンセルは `DownloadError` のまま、`fragment_index / fragment_count` からの割合と追いついた判定、停止後に成功の経路で終わる。
- `test_live_recorder.py`(新規)
  - ffmpeg のコマンドライン(入力1つ・2つ、ヘッダー)、`-progress` の出力の解析、`q` での停止とタイムアウト時の強制終了、終了コード 0 以外でも中身があれば保存、再格納のコマンド。
- `test_widgets.py`: ライブ表示、`percent < 0` で不定表示、ボタンの文字と `stop_requested`。
- `test_main_window.py`: ライブ判定による表示の切り替え(バッジ・録画開始位置の行・隠す項目・ボタンの文字)と元に戻すこと、固定領域への出し入れ、停止の確認、終了時の確認文と保存待ち。

## 対象外

- 配信予定(`is_upcoming`)の配信開始を待っての自動録画。
- ライブチャットの保存。
- YouTube 以外のサイトのライブ配信(yt-dlp の判定でライブになれば動く可能性はあるが、確認・保証はしない)。
- アプリのクラッシュ時に作業フォルダに残った録画の救出(既知の問題「作業フォルダが残る」と同じ扱い)。
